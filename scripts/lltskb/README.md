# 路路通时刻表 · 数据格式与 CSV 导出说明

本文记录 `an.db` 这个"数据库文件"的真实格式，以及如何从零把它导出成 27 个可读 CSV。

- 适用版本：路路通 5.3.8，数据日期 `20261114`（`an.db` 2,334,434 字节）
- 所有结论均以**字节级验证**为准：每个文件的解析指针都恰好落在文件末尾，且交叉计数互相吻合（见第 6 节）

---

## 1. 数据从哪来

```
http://down.lltskb.com/android.ver      ← 版本清单（UTF-8 带 BOM 的 JSON）
http://down.lltskb.com/an.db            ← 数据包，2.3 MB
```

`android.ver` 里的关键字段：

```json
"version": { "app": "5.3.8", "data": "20261114", "minSdk": 19 },
"dataUrl": ["http://223.107.87.50:8011/an.db", "http://down.lltskb.com/an.db"]
```

App 的判定逻辑（`com.lltskb.lltskb.model.upgrade.UpgradeModel`）：把 `version.data` 和本地
`<files>/ver.txt` 做字符串比较，远程更新则按 `dataUrl` 数组顺序下载，存成 `lltskb.db`，
就地解压到私有目录，删掉 zip，再 `ResMgr.init()` 重载。**不校验长度/MD5/签名，也不支持断点续传。**

> `an.db` 不是 SQLite。魔数是 `PK\x03\x04`，它是一个 ZIP。

两个坑（`fetch.py` 已处理）：

- `android.ver` 是手写的，不一定是合法 JSON（实测出现过 `"name": 应用宝",`），只能用正则取字段。
- 镜像 `223.107.87.50:8011` 上也有一份 `android.ver`，但停在 `20230525`，不能信；
  它的 `an.db` 倒是新的。所以版本只看 `down.lltskb.com`，下载后再用包里的 `ver.txt` 核对。

## 2. 三步复现

以下命令都在本目录（`scripts/lltskb/`）执行，只需要 Python 3 标准库，无第三方依赖。

```bash
# ① 取版本清单，确认最新 data 版本号
python3 fetch.py --check      # -> 20261114

# ② 下载 an.db 并解压到 ./an/（本地已是最新版则跳过，--force 强制）
python3 fetch.py

# ③ 导出 CSV
python3 export_csv.py an csv
```

`export_csv.py` 默认读写同目录下的 `an/` 和 `csv/`，所以 `python3 export_csv.py` 即可。
完整跑完约 2 秒，输出 27 个 CSV + 1 个说明文件，合计约 58 万行 / 21 MB。
`an.db`、`an/`、`csv/` 是第三方数据，不进 git，也不对外发布。

配套脚本：

| 文件                | 用途                                                                |
| ------------------- | ------------------------------------------------------------------- |
| `fetch.py`          | 查上游版本、下载并解压 `an.db`                                      |
| `export_csv.py`     | 全量导出 CSV，并做第 6 节的自检，不过则退出码 1                     |
| `lulutong_parse.py` | 最小查询器：`train G1` / `query 北京南 上海虹桥` / `station 北京南` |
| `build_d1.py`       | 生成导入 D1 的 SQL，供 Worker 的 `/api/v1/cr/*` 接口使用（见下）    |

### 在构建里（`scripts/build`）

构建把上游数据版本号（`fetch.py --check`）当作一个数据源的版本钉住，版本变了才重跑：

```bash
python3 fetch.py --version 20261120 --db <an.db> --out <an 目录>
```

`--db` 指向的 `an.db` 已存在就直接用，否则从上游下载到那里；包里的 `ver.txt` 不是
`--version` 指定的版本就报错退出。上游只保留最新版，所以构建把每个版本的 `an.db`
留在自己的存储里（不再发 GitHub release），旧版本只能从那里取；改了导出脚本也能据此重导。
之后依次是 `export_csv.py`（自检失败则这一步失败）、把车站对到 OSM
（`../stations/cr-station-trains.py`）、`build_d1.py` 生成 SQL，最后导入 D1。

### 导入 D1（Worker 的 `/api/v1/cr/*` 接口）

Worker（`src/worker/api/cr.ts`）的 `/api/v1/cr/stations`、`/api/v1/cr/trains` 从 Cloudflare D1
数据库 `cr` 读数据，接口说明见 [`public/api/v1/doc.md`](../../public/api/v1/doc.md#china-railway)。
`build_d1.py` 生成的 SQL 把当前版本导入 D1：

```bash
python3 build_d1.py an <cr-station-trains.csv> cr.sql   # 约 55 MB，约 4.7 万行
npx wrangler d1 execute cr --remote --file=cr.sql        # 在仓库根目录（wrangler.toml 所在处）
```

- **存的是预先算好的答案**：每个车站一行（太大时拆成几段），存所有在此停靠的车次；
  每个车次号一行，存它的全部停站、经由线路和车底（`jlb.dat`，按套跑车次组对上）。车次保留
  开行起止、周期和带日期的车底，由 Worker 按查询日期筛选。
- **经由线路**：`routes.dat` 的车次路径（经 `sp.dat` 的 12306 内部号对上）只给换线站，
  `build_d1.py` 沿各线路的车站表走一遍，得到途经的每个车站及里程。线路车站表不含小站，
  停站以时刻表为准：表里有的停站用作锚点（里程取时刻表的累计里程，中间站按线路里程比例插值），
  没有的按里程插进去。路径起讫与车次始发、终到对不上的（约 1%）不给线路。
  所以一次请求只是一次主键查询，每次导入写约 4.7 万行，在免费额度（每天 10 万行）以内。
- **车次号与方向标签**：车站时刻表的每一条带上本站的到达/出发车次号（`xw.dat`，见 4.12）
  和到发线路。线路取离本站 50 km 处所在的线路（越过站旁的联络线）；那里若是联络线或枢纽内的线路
  （`HUB_LINES`，如上海枢纽的虹封线、黄南线），改取它与本站之间的线路，本站也在枢纽内时取枢纽外的下一条
  （G8354 到太仓的线路是沪苏通，不是虹封）。按显示名归并
  （`DISPLAY`、`SAME_LINE`）。路路通的经由线路有时把普速线和旁边的高铁/客专弄混
  （北京西、石家庄的 京广线/京广高铁，同一车次往返两个方向说法不一），`build_d1.py` 按
  `TWINS` 纠正：G 字头只走高铁，K/T/Z/N/V/Y/L/S 和纯数字车次只走普速；D/C 字头在
  回程车（起讫对调、车次号各差 1）说的是另一条时，CR200J 归普速，其余归高铁。
  京沪线/沪宁高速只在南京—上海、京九线/昌九城际只在九江—南昌之间算一对（`TWIN_STRETCH`）。
  上行/下行由本站车次号的奇偶决定（单数下行）。
- **车次搜索**：`cr_search` 表按车次号排序存每个车次的始发、终到和开行起止（约 20 行），
  Worker 的 `/api/v1/search` 整表读进内存，数据版本变了才重读，之后每次搜索只读一行版本号。
- **OSM 对照**：`cr-station-trains.csv`（`../stations/cr-station-trains.py` 的输出）给出
  OSM 元素 → 车站名，地图可以直接用要素的 OSM id 查时刻表。
- **按版本切换**：表名带数据版本（`cr_trains_20261114`），文件最后才把 `cr_*` 视图指向新表，
  导入中途失败时仍由旧版本服务；成功后删掉其他版本的表。同一版本重新导入时，
  导入期间这些接口会返回 503。

一次性配置：

1. `npx wrangler d1 create cr`，把输出的 `database_id` 填进仓库根目录 `wrangler.toml` 的
   `[[d1_databases]]`（binding 必须是 `CR_DB`），再部署 Worker。
2. 在 D1 控制台的 Settings 里开启 Read Replication，让各地的读请求走就近副本。
3. 由构建导入 D1 时，仓库 Secrets 需要 `CLOUDFLARE_API_TOKEN`（含 D1 编辑权限）和
   `CLOUDFLARE_ACCOUNT_ID`。

## 3. 三个必须先知道的编码约定

不先掌握这三条，后面所有文件都读不出来。

### 3.1 两字节整数是 `hi*255 + lo`（不是 256）

```python
def k(b, o):
    return (b[o] & 0xFF) * 255 + (b[o + 1] & 0xFF)
```

App 里的 `DataMgr.OooOOo0()` 就是这个。取值范围 0–16383，正好覆盖 3330 个站和 15131 个车次。
极少数文件（`p*.dat`）用的是 `hi*128 + lo`，读的时候要看清楚是哪个类实现的。

### 3.2 日期是 4 字节 base-128 小端

```python
def date4(b, o):
    return ((b[o] & 0xFF) + (b[o+1] & 0xFF) * 128
            + (b[o+2] & 0xFF) * 16384 + (b[o+3] & 0xFF) * 2097152)
# b'\x1f\x4a\x54\x09' -> 20260127
```

等价于把 4 个字节各取 7 位拼成 28 位整数。反编译里显示成
`(long)(b0 + b1*128 + b2*16384) + (long)b3 * 2097152`，别被 jadx 的 `UByte.MIN_VALUE` 误导。

`20501231` 是"长期开行"的占位值，不是笔误。

### 3.3 分片寻址：索引来自排序位置，不是名字

| 要找什么          | 怎么定位                                       |
| ----------------- | ---------------------------------------------- |
| 站 `i` 的车次表   | `S{(i+1) % 10}.dat`                            |
| 车次 `i` 的停站表 | `T{(i+1) % 20}.dat`                            |
| `i` 本身          | 该站在 `s.i` / 该车次在 `t.i` 里的**排序位置** |

`t.i` 是按字符串排序的，所以 `G1` 的位置是 6119 —— 名字和位置没有任何直觉关系，别猜。

## 4. 逐文件格式

字符集全部 UTF-8；字符串前缀长度是**字节数**，不是字符数。

### 4.1 `s.i` / `t.i` — 车站、车次索引

```
[u16 条数]  ( [u16 长度][UTF-8 字节] ) × 条数
```

`u16` 是标准大端（Java 的 `DataInputStream.readShort` + `readUTF`），**不是** 3.1 的 ×255 变体。
`s.i` 3330 条（按拼音排序），`t.i` 15131 条（按字符串排序，`C481/C484` 这种是同一列车上下行双号）。

### 4.2 `S*.dat` — 站 → 车次（候选集）

```
记录 = [站索引(2)] [条数(2)] [条数 × 车次索引(2)]
```

10 个文件 × 333 条 = 3330，每个站恰好出现一次。

**重要：这是候选集，包含"通过不停"的车。** 全量 184,664 对里只有 143,594 对真正办客。
查站站时用 S 缩小范围，再用 T 的停站表确认，不在停站表里的直接丢弃 —— 这就是
`QueryBase.getTrainTimeDTO()` 在 `from/to` 缺失时返回 `null` 的原因。

### 4.3 `T*.dat` — 车次 → 停站（核心）

```
记录 = [车次索引(2)] [头 15 字节] [停站 7 字节 × N]
```

头部：

| 偏移  | 长度 | 含义                                            |
| ----- | ---- | ----------------------------------------------- |
| 0     | 1    | 列车类型号（G=6 等，UI 里其实优先看车次首字母） |
| 1–2   | 2    | 票价号 priceNo（0 表示按里程现算）              |
| 3–6   | 4    | 开行起 yyyyMMdd（base-128）                     |
| 7–10  | 4    | 开行止 yyyyMMdd                                 |
| 11–12 | 2    | 开行周期号，索引进 `t.rule`                     |
| 13–14 | 2    | 停站数 N                                        |

停站（每站 7 字节）：

| 偏移 | 长度 | 含义                 |
| ---- | ---- | -------------------- |
| 0–1  | 2    | 站索引（×255）       |
| 2    | 1    | 到达时               |
| 3    | 1    | 到达分               |
| 4    | 1    | 停留分钟             |
| 5–6  | 2    | **累计**里程（×255） |

G1 的真实字节：

```
17fe | 06 0000 1f4a5409 6f256309 0000 0007 | 00ab 06 1e 00 0000 | 00db 07 12 02 00d2 ...
车次 | 类型 票价 20260127  20501231 周期 7站 | 北京南 06:30 停0 0km | 沧州西 07:18 停2 210km
```

三个**不存**、必须算的字段：

- **发车时刻** = 到达 + 停留分钟（满 60 进位）。始发/终到站停留为 0，所以发车=到达。
- **站序** = 数组下标。
- **运行天数** —— 完全没有。跨夜车次的时间仍然写成 `06:45`，靠"发车小时比上一站小"推断。
  导出时我用 `arr_min < prev - 600`（回退超 10 小时）判断跨天，写在「推算运行天数」列。

四个边界情况（实测计数）：

- 环形/折返车次同站出现两次 → **91 个**，靠数组位置和里程（0 vs 727）区分，不要按站名去重
- 旧数据缺里程 → 尾 2 字节为 0 时，App 把那两个字节当"停站序号"用（**85 个车次**），
  不处理的话这些车次的里程会全变 0
- 最长记录 49 站（`K551/K554` 佳木斯→温州，3645 km，整条 360 字节）
- `sch.dat`（0 字节）是停运/临调覆盖层，用 9/12 字节变长记录，有数据时要覆盖基础停站

### 4.4 `t.rule` — 开行周期

纯文本，每行 `周期 位掩码`，共 162 组：

```
1 1        ← 每天
10 517     ← 10 天一轮，倒推天数 % 10 落在 517 的二进制位上才开行
```

判定：`(endDate - 查询日).days % period` 取位，与 mask 相与。忽略这一步会把停运日的车也列出来。

### 4.5 `sp.dat` — 内部编号与车站属性

六段，计数有的是 4 字节大端（`struct.unpack('>i')`），有的是 2 字节 ×255，逐段如下：

1. `i32 n` + `16 字节 × n`：临时调整条目（id, 起, 止, 值1, 值2）
2. `i32 n` + `(1B 长度 + 字符串) × n`：**12306 内部车次号**，如 `24000000G10L`，与车次索引一一对应
3. `2B n` + `(2B 城市号 + 1B 长度 + 字符串) × n`
4. `i32 n` + `8 字节 × n`：省/地区归属（站索引 + 两个编号）
5. `i32 n` + `(2B 站号 + 1B 长度 + 字符串) × n`：车站地理位置
6. `i32 n` + `(1B 长度 + "名,值") × n`：补充位置别名

### 4.6 `routes.dat` — 路网

```
i32 线路数
  i32 线路代码 + 字符串 线路名 + i32 站数
    ( 字符串 站名 + 字符串 电报码 + i32 分界标志 + i32 里程 ) × 站数
i32 车次路径数
  字符串 12306内部号 + 字符串 终到站 + i32 段数
    ( 字符串 站名 + i32 线路代码 ) × 段数
```

797 条线路、14,997 条车次路径。第一段记录是表头占位（"线路名"/"车站名"/"略号"）。
G1 = 北京南 上 `京沪高速线`（代码 342）直达上海虹桥，一段走完。

### 4.7 `plat.dat` — 站台 / 检票口

```
i32 n ;  n × ( i32 车次索引 + i32 站索引 + 1B 长度 + 字符串 )
```

96,391 条，key 是 `(车次, 车站)`，例如 `(6119, 171) → "17"`。

### 4.8 `sn.dat` — 同城分组与电报码

```
u16 n1 + (u16 长度 + 字符串) × n1          搜索别名，74 条
u16 n2 + ( u16 组号 + 1B 个数 + i16×个数 ) × n2    同城车站组，658 条
u16 n3 + ( 1B 长度 + "站名-电报码" ) × n3        364 条
```

第二段用**有符号** `readShort`，别用 ×255 解。

### 4.9 `extra.dat` — 单位、复兴号、折返、市域

按顺序六段（计数都是 2 字节 ×255）：

1. 企业/单位名表（373 条）
2. `( 车次(2) + 单位号(2) + 1B 站数 )`，站数 >0 时再跟站级检票口（起始日、结束日、1B 长度 + 文本）。
   **本版数据 15,021 条记录站数全为 0**，等于没有检票口明细。
3. 复兴号类型 1 / 2 / 3 三段（4,133 / 330 / 804 条）
4. 折返/套跑站序（1,072 条）
5. 市域线车次（122 条）

### 4.10 `jlb.dat` — 车底与餐车

```
i32 n ; n × ( 4B 起 + 4B 止 + 4B 标志1 + 4B 标志2 + 2B 担当单位
             + 1B 长度 + 车型/供电串 + 1B 长度 + 套跑车次组 )
i32 nf ; nf × ( 4B 车次 + 4B 起 + 4B 止 + 1B 长度 + 餐车串 )
```

3,750 组车底（key 是 `Z16#Z15` 这种车次组，不是车次索引）+ 14,194 条餐车位置。

- 担当单位（×255）是 `extra.dat` 企业/单位表的下标（0 = 暂无），例如 4 = 哈局哈尔滨段；
  与 `18_车次所属单位.csv` 对照，1,634 个能对上的车次里 1,628 个一致。
- 车次组里的简写：`K2153/2` = K2153 和 K2152，`G1240/37` = G1240 和 G1237，`4172/3/4` 三个车次；
  `0` 开头的（`0K1062`）是车底回送。
- 车型/供电串是手写文本：`CRH380BG型重联`、`25G型,DC600V,双管供风,集便,襄阳调向`，
  还会混入调向、高峰线等备注，备注里的车次可能是同组套跑的其他车次。**没有车组号。**

### 4.11 `p*.dat` / `pk*.dat` — 票价覆盖

```
p  : [键(2, hi*128+lo)] [键(2)] [1B 条数] ( 6 字节 × 条数 )
pk : [键(2, ×255)] [键(2)] [1B 条数]
     ( 2B 席别键 + 1B 标志 + bitcount(标志)*2 字节 ) × 条数
```

`bitcount` 权重：bit1/2/16/32 各 1 个字段，bit4 算 3 个，bit8 算 2 个。

**这两张表极小**（25 + 262 条），因为绝大多数车次 `priceNo = 0`：真实票价是按里程阶梯
在 `com.lltskb.lltskb.engine.PriceQuery` 的 `int[][]` 里现算的。

### 4.12 `xw.dat` — 双车次在哪一站换号

```
u16 n（×255）
n × ( 车次索引(2) + 未知(2) + 1B 条数 + 条数 × ( 里程(2) + 1B 车次序号 ) )
```

14,953 条，正好读到文件末尾。每条记录给出从某个**累计里程**起，车次按 `车次名.split("/")`
的第几个号开行：`Z156/Z157B` 是 `(0, 1) (94, 0) (1629, 1)`，即泰州 Z157、东台起 Z156、
山海关起 Z157。App 的 `QueryBase.get_exact_train_name` 取里程不超过本站的最后一条；
换号站 App 显示「旧号/新号」（东台 `Z157/Z156`）。单车次的记录为空；4,596 个双车次里
4,578 个有记录，其余（多为 Y 字头旅游列车）和记录越界的，App 全程显示第一个号。
「未知」两字节不是餐车位置，含义未确证。

### 4.13 其余

## 5. 导出脚本怎么组织的

`export_csv.py` 是单文件、零依赖，结构自上而下：

1. **解码原语**：`k()` / `date4()` / `i32()` / `u16()` / `read_index()` / `read_s_dat()` / `read_t_dat()`
2. **一次性装载**：`s.i`、`t.i`、10 个 S 分片（合并成 `站 → [车次]`）、20 个 T 分片（合并成 `车次 → (头, 停站)`）
3. **派生索引**：`t_stop_idx = 车次 → {站: [站序]}`，后面标注"是否办客"用它
4. **逐表写出**：每个 CSV 通过 `open_csv(文件名, 表头, 说明, 来源)` 打开，函数顺便登记行数，
   最后汇总成 `00_导出说明.csv`
5. 输出编码 `utf-8`（**无 BOM**）。要让老的 Excel 识别，可用「数据 → 从文本/CSV → UTF-8」导入

想加一个新视图，照抄这一段即可：

```python
f, w, m = open_csv("28_我想要的.csv", ["车次", "车站"], "说明", "T*.dat")
for ti, (head, blob) in tinfo.items():
    for s in parse_stops(blob):
        w.writerow([TN(ti), SN(s["st"])])
        m[3] += 1
f.close()
```

`SN(i)` / `TN(i)` 是站名/车次名查表，`TN` 在越界时返回 `#序号` 而不是抛异常。

## 7. 已知不确定项

1. **`p`/`pk` 票价表的字段语义没完全确证**：key 是 `(站,站)`、条目 6 字节、`priceNo % 5` 选文件
   这些是确定的，但每个字节代表哪个席别没有权威对照。`p*.dat` 的现有解法读不到文件末尾
   （`20261114` 版 5 个文件都剩几十到一百多字节），说明记录结构还没摸清，所以自检跳过了它。
2. **`ime.dat` 结构未知**，且 App 不读它，CSV 里是强解的可读文本。
3. **`extra.dat` 的站级检票口本版全空**，检出 0 行不是脚本 bug。
4. **跨夜天数** 是推算值（原始数据不存），跨多天的超长车次仍可能算错一天。
5. `sch.dat`/`ts.dat` 有内容时需要额外的覆盖合并逻辑，本版为空所以未实现。

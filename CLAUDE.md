# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-user fork of Atlas Realm: a MapLibre map with an OpenRailwayMap overlay, built with Vite and served by one Cloudflare Worker. Upstream's collaboration stack (Durable Object rooms, D1 accounts, GitHub OAuth, the agent CLI and its skills) has been removed. The worker serves static assets, vector tiles and the API under `/api/v1` (timetables, trains, routes and relations). Layers (imported GPX/GeoJSON) and annotations (markers, text, lines, areas, routes, weather cards) live in browser memory only and are lost on reload unless exported.

Node 22, pnpm, TypeScript (`strict: false` but `noImplicitAny: true`). Formatting is oxfmt (single quotes, semicolons, 120 cols; `scripts/styles/**` uses no semicolons). Linting is oxlint.

## Commands

```bash
pnpm dev                 # Vite dev server with the Cloudflare plugin (worker runs locally)
pnpm build               # vite build -> dist/
pnpm preview             # build + wrangler dev
pnpm run deploy          # build + wrangler deploy (`pnpm deploy` is a different, built-in pnpm command)
pnpm typecheck           # tsc --noEmit (covers src/ only)
pnpm lint / lint:fix     # oxlint
pnpm fmt / fmt:check     # oxfmt
pnpm test                # unit tests: src/**/*.test.ts and scripts/**/*.test.mjs
./scripts/test-python.sh # Python tests of the data scripts and the build runner (scripts/*/test_*.py)
pnpm test:e2e            # Playwright (starts its own server, see below)
pnpm generate:style      # regenerate public/orm/style/standard.json from scripts/styles/

python3 scripts/build/build.py plan             # the data build: what would run, why, and about how long
python3 scripts/build/build.py run [step ...]   # bring steps up to date (no deploys without --deploy)
python3 scripts/build/build.py run --checks     # the tests whose files changed since they passed
```

The tests are steps of the data build (`check-format`, `check-lint`, `check-types`, `check-unit`, `check-e2e`, and `check-build`, `check-extract`, `check-lltskb`, `check-relations`, `check-routing` for the Python tests): `python3 scripts/build/build.py run --checks` runs the ones whose files changed since they last passed, several at a time. CI runs them all on pull requests (`.github/workflows/test.yml`, which has no state to tell what passed) and, on pushes to `main`, the changed ones inside the Build workflow. The Python tests of `scripts/relations/` and `scripts/routing/`, and most build steps, need `osmium` and the packages in `scripts/requirements.txt` (pyosmium, numpy, scipy, shapely); on NixOS run them in `nix-shell scripts/routing/shell.nix`.

Running a single test:

```bash
pnpm vitest run --config vitest.config.js src/gpx.test.ts -t 'name substring'
pnpm exec playwright test e2e/annotations.spec.ts --project chromium
```

Test conventions:

- `*.dom.test.ts` files opt into happy-dom with a `// @vitest-environment happy-dom` header; other unit tests run in Node.
- `*.mobile.spec.ts` only run in the `mobile-chromium` Playwright project (Pixel 7); other specs run in `chromium`.
- Playwright's web server starts Vite with `SCREENSHOT_FIXTURES=1` and `CLOUDFLARE_VITE_REMOTE_BINDINGS=0`. Set `PLAYWRIGHT_BASE_URL` to test an already running server instead. `e2e/support/` holds the shared fixtures (map fixture with mocked external services, map interaction helpers, UI invariant audit).
- Locally (NixOS) Playwright's downloaded browsers do not exist, so run the e2e tests on the system Chromium, which also turns videos off (they need Playwright's ffmpeg):

  ```bash
  PLAYWRIGHT_CHROMIUM_EXECUTABLE=$(readlink -f $(which chromium)) pnpm test:e2e
  ```

  Behind an HTTP proxy (`HTTP_PROXY` set, as in Claude Code's sandbox) also set `NO_PROXY=127.0.0.1,localhost`: otherwise the proxy answers Playwright's check of the web server URL, Playwright takes the server as already running and never starts Vite, and every test fails with `ERR_CONNECTION_REFUSED`.

Local dev environment notes:

- The R2 bucket binding is `remote: true`, so `pnpm dev` uses remote Cloudflare bindings by default (needs wrangler auth). Set `CLOUDFLARE_VITE_REMOTE_BINDINGS=0` to run fully offline (tiles will not load).
- The Worker bundles two station files the data build makes. Without a build in this checkout (`.build/out/`) or `JP_STATION_CODES` / `STATION_COORDS` set, `vite.config.js` falls back to the few stations of the test fixtures, so the local API answers most Japanese stations without OSM features; `gh run download <run-id> -n build-outputs -D .build/out` fetches a Build run's files.

## Architecture

### Worker (`src/worker.ts` -> `src/worker/`)

`src/worker.ts` only re-exports `src/worker/entry.ts`, which handles CORS preflight, serves `/tiles/*` from PMTiles archives in R2 (`src/worker/tiles.ts`, range reads plus the Workers cache; versioned tile URLs, empty ones included, are `immutable` for a year so browsers reuse them without invoking the Worker, which is why the version in the URL must change with every archive: `/tiles/<archive>/version` answers the start of the archive's R2 ETag, fresh for a minute and never from the Worker's cache), hands `/api/*` to the API (`src/worker/api/`, below), and falls back to static assets from `dist/` with SPA fallback. The bindings are `ORM_BUCKET` (R2), `ASSETS`, `CR_DB` (the D1 database `cr`, remote in `pnpm dev` like the bucket) and `NORIKAE` (the `NorikaeApi` Durable Object).

### API (`src/worker/api/`)

The JSON API the map reads, documented in `public/api/v1/doc.md` (served as `/api/v1/doc.md`). Japanese routes, stations, timetables and trains under `/api/v1/norikae` are scraped from Yahoo! 乗換案内 (`norikae/routes.ts`, `norikae/timetable.ts`, `norikae/handlers.ts`) inside the `NorikaeApi` Durable Object, placed in Japan because Yahoo answers 403 to some regions; so are China Railway trainsets (`/api/v1/cr/trainsets`, live from 12306). China Railway timetables and train routes (`/api/v1/cr`, `cr.ts`), relations (`/api/v1/relations`, `relations.ts`) and search (`/api/v1/search`, `search.ts`) read D1 at the edge; a Yahoo train's route (`train-route.ts`, `jp-assemble.ts`) takes the train's stops from the object and the hops from D1. `runtime.ts` is the only module tied to the Workers runtime (upstream fetch with edge caching, D1 sessions, the Durable Object); the rest takes the fetch and query as arguments, so the tests run them in Node against fixtures (`src/worker/api/fixtures/`, with `*.expected.json` frozen from the Python Worker this was ported from) and `node:sqlite`. Every answer about a Japanese station carries its OSM features and position from `jp-station-codes.csv` and `station-coords.csv`, bundled with the Worker (`osm-stations.ts`). Those two are outputs of the data build, not files in git: `osm-stations.ts` imports them as `station-data/…?raw`, an alias `vite.config.js` points at `JP_STATION_CODES` / `STATION_COORDS`, else at `.build/out/<step>/`, else at `src/worker/api/fixtures/stations/` (the stations the other fixtures name), which is what `vitest.config.js` always uses. The D1 data is built and imported by the data build (below); the scripts' own tests assert that the SQL fixtures here (`cr-*.sql`, `cr-routes-*`) are what they write (`UPDATE_FIXTURES=1` regenerates them).

### Data build (`scripts/build/`)

Everything the Worker serves besides the app comes from one build: the tile archive in R2, the D1 database `cr` (China Railway timetables and train routes, relations, Japan's route hops) and the two station files the Worker bundles. `scripts/build/build.py` (standard library only; its docstring is the reference) runs the steps declared in `scripts/build/steps.toml`, which opens with a diagram of the graph. The checks and the deploys are steps of the same graph.

**The graph.** OpenStreetMap comes in through one pass over the weekly planet; everything else hangs off it or off the timetable:

| Step                                                                                     | Makes                                                                                                                                                                                               | From                                                                                        |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `planet-extract`                                                                         | `world.osm.pbf`: railway ways and railway relations worldwide, without nodes; `box.osm.pbf`: the railway objects of the box around China and Japan (72,16,147,55) with their nodes                  | the planet, streamed once (`scripts/extract/filter-planet.sh`, ~30 min)                     |
| `hourly-diffs`                                                                           | the hourly diffs since the planet up to the pinned sequence, filtered to railway objects, and their `timestamp`                                                                                     | `scripts/extract/fetch-diffs.sh`                                                            |
| `railway-extract`                                                                        | `lines.opl`: line relations and tagged ways, for the tiles                                                                                                                                          | `world.osm.pbf` + the diffs                                                                 |
| `box-extract`                                                                            | `cnjp.osm.pbf` (73,17,146,54) and its `timestamp`, read by everything below that needs coordinates                                                                                                  | `box.osm.pbf` + the diffs                                                                   |
| `lltskb`, `cr-timetable`                                                                 | 路路通's timetable as CSV; its D1 SQL                                                                                                                                                               | `scripts/lltskb/`                                                                           |
| `osm-stations`, `cr-station-trains`, `jp-station-codes`, `station-coords`                | the box's stations; the station files                                                                                                                                                               | `scripts/stations/`                                                                         |
| `n02`, `line-groups`                                                                     | Japan's official lines                                                                                                                                                                              | MLIT's N02, `cnjp.osm.pbf` (`scripts/lines/`)                                               |
| `relations`                                                                              | the answers of `/api/v1/relations`, as D1 SQL                                                                                                                                                       | `cnjp.osm.pbf`, `line-groups` (`scripts/relations/`)                                        |
| `routing-graph`, `cr-routes`, `jp-hops`                                                  | trains' routes on OSM track, as D1 SQL                                                                                                                                                              | `cnjp.osm.pbf`, the timetable, the station files (`scripts/routing/`)                       |
| `tiles`                                                                                  | `openrailwaymap.pmtiles`                                                                                                                                                                            | the import database image, `lines.opl`, `line-groups`, the station files (`scripts/tiles/`) |
| `check-*`                                                                                | nothing: the tests (`check-format`, `check-lint`, `check-types`, `check-unit`, `check-e2e`; `check-build`, `check-extract`, `check-lltskb`, `check-relations`, `check-routing` for the Python ones) |                                                                                             |
| `deploy-timetable`, `deploy-relations`, `deploy-routes`, `deploy-tiles`, `deploy-worker` | nothing here: D1 imports (`scripts/build/d1-import.sh`), the R2 upload, the Worker                                                                                                                  | the outputs above                                                                           |

Why the extract is shaped like this, so it is not undone: a planet way's coordinates are on nodes that come before it in the file, and the planet (~96 GB) does not fit on a runner, so one stream cannot keep only the nodes the railway ways use. The tiles need none (they join relation and way tags to the import database's ways by id), and everything that needs coordinates is inside the box, so the pass cuts the whole box with its nodes to disk (`osmium extract -s simple`, beside the worldwide filter on the same download through a fifo) and filters it afterwards. That cut keeps a relation only when a member node is inside, so routes of ways alone (most of India's trains) and route masters are added back from `world.osm.pbf` with `osmium getparents`, twice. A second planet pass for the nodes took twice as long, and Geofabrik's regional files come to GitHub runners at ~2 MB/s. Filtering one hourly diff takes 1-2 GB, so the diffs are fetched once, four at a time, and both extracts apply them with `osmium apply-changes`: two diff updates side by side ran the 16 GB runner out of memory. Diffs keep what was deleted from OSM since the planet, so a deleted object lingers until the next weekly planet. Both planet passes print their progress every three minutes (`scripts/extract/meter.py`).

**Up to date.** A step names everything it reads: `files` of this repository (globs; a directory stands for its files; `.` for the whole repository; only files git tracks or would add count; `!pattern` excludes), `sources` (data from outside) and `needs` (other steps' outputs, `step/output`, read at `$BUILD/<step>/<output>`). It writes its declared `outs` into `$OUT`, which becomes `.build/out/<step>/` once it succeeds (a failed step leaves its last good outputs). It is up to date when the hash of its command and of the content of all it reads is the one it was last built with, so a step that writes the same output again leaves its readers alone. The step file is checked when loaded: unknown keys, a command reading a `$BUILD/<step>` or `$SRC_<NAME>` it does not declare, a pattern matching nothing and cycles are errors, which keeps the dependencies honest: add what a command reads to its lists, not around them.

**Sources** are pinned: `lltskb` (路路通's data version), `planet` (the dated weekly planet), `osm-diffs` (the hourly sequence), `orm-db` (the import database image's digest) and `yahoo-stations` (no probe). A build reads the pins, and only `--refresh` (names, or `all`) probes again, so a push rebuilds what the commit touched and a refreshed build what changed outside. Steps get the pinned version as `$SRC_<NAME>` and must build from exactly it (the dated planet URL, diffs up to that sequence, the image by digest, that version's `an.db`). The store (`$STORE`, a step's `store` list) is what a step keeps between runs: each `an.db` version, since upstream serves only the latest, and the Yahoo search cache, which `jp-station-codes` searches only new names past; refreshing `yahoo-stations` starts a new one.

**Running.** Steps run several at a time: one starts when what it needs and comes `after` is done and the machine holds it, by the `cpus` and `memory` (GB, 1 each unless said) it declares against `--cpus`/`--memory` (the machine's by default); a step bigger than the machine runs alone, deploys run one at a time, and a step is not rerun while one reading its outputs runs. Declare the memory a step really peaks at: the runner has 16 GB, and an out-of-memory runner only says it "lost communication". A run (and `plan`) opens with how many steps it has and, when all have run before, an estimate from their last times put through the same scheduling (`simulate`); output lines carry their step's name, and every minute a line says what is running and for how long (`--report`). Checks (`check = true`) write nothing and run again only when their files change; a failing check holds back only the deploys that list it in `after`. Deploys (`deploy = true`) write nothing and run only with `--deploy`, after the deploys and checks in their `after`: `deploy-routes` after `deploy-timetable`, `deploy-worker` after every other deploy and every check of the app, so code never goes out untested or before the data it reads. A deploy whose `after` failed waits, unless only data from outside holds it back (the failing steps have the command and files they last built with).

**State.** `state.json` (the pins, the declared graph, and per step the hashes of what it read, the hash and size of each output and of each file in an output directory, when, how long, and its last attempt) decides what is up to date, not the files in `.build/out`: a lost output is rebuilt only when a step that has to run reads it (once, however many of its outputs it reads), and an output that is not the recorded one is rebuilt. `prune` deletes the outputs of `keep = false` steps (`lltskb`, `cr-timetable`, `routing-graph`, `cr-routes`, `tiles`: the large ones, and all holding 路路通's timetable, third-party data never committed, published or left in the CI cache of this public repository) once nothing still to run reads them; while deploys are off the tile archive (3.9 GB) therefore stays cached. `adopt step ...` records steps as built from what is in their output directories, or a deploy as done.

**CI.** The Build workflow (`.github/workflows/build.yml`, one job, one run at a time) frees disk, restores the newest `.build/out` cache, runs `build.py run --deploy`, uploads the station files and the official lines' review as the `build-outputs` artifact, prunes, saves the cache under the run's key and deletes the older ones. It runs on pushes to `main` (pins as they are), every three days (`--refresh all`), and by hand (inputs `refresh`, `force`, `targets`, `deploy`, `plan_only`); pushes and scheduled runs deploy while the repository variable `BUILD_DEPLOY` is `true` (it is). `BUILD_REMOTE=s3://orm/build` keeps the state in R2 after every step, so a lost cache costs time but no redeploy. Secrets: `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_ACCOUNT_ID` (`scripts/tiles/set-r2-secrets.sh`), `CLOUDFLARE_ACCOUNT_ID`, and `CLOUDFLARE_API_TOKEN` with Workers Editor on `map`, D1 write, the `orm` bucket, and Zone Read plus Workers Routes Write on `shz.al` (without the zone rights `wrangler deploy` uploads the Worker, then fails on the custom domain). A full rebuild takes about 1.5 hours (the planet pass ~30 min, the tiles ~30-40, China's routes ~15-25); a push touching only the app takes its checks and a deploy.

**Adding a step:** a `[steps.<name>]` table with its command and everything the command reads, `needs` on it from its consumers, `cpus`/`memory` if it is heavy, `keep = false` if its outputs are large or hold the timetable, and a deploy's `after` on its checks; check with `build.py plan`. `scripts/build/test_build.py` tests the runner on small step files.

### Data files

Generated data is not in git; `data/` is empty. Where each kind lives:

- **Build outputs**, `.build/out/<step>/` (git-ignored; on CI in the Actions cache): the extracts, the SQL, the tile archive, and the station files `cr-station-trains/cr-station-trains.csv`, `jp-station-codes/jp-station-codes.csv` and `station-coords/station-coords.csv`. Each Build run also uploads the station files and the official lines' review as its `build-outputs` artifact; `gh run download <run-id> -n build-outputs -D .build/out` puts them where the local build and `vite.config.js` look.
- **The Worker's station files** come in through the `station-data/` alias (`vite.config.js`): `JP_STATION_CODES` / `STATION_COORDS`, else `.build/out/<step>/`, else `src/worker/api/fixtures/stations/` (a few stations, what the tests always use).
- **R2, bucket `orm`**: `openrailwaymap.pmtiles` (the tiles; `openrailwaymap-test-*` from bounding-box test runs), and under `build/` the build's `state.json`, `runs/<run id>.json` (one report per CI run, which the dashboard lists) and `store/` (`lltskb/<version>/an.db`, `yahoo-stations/<version>.json`).
- **D1, database `cr`**: tables named by data version behind views the imports switch last (`cr_*` the timetable, `osm_relations`, `route_cr_*` and `jp_*` the routes); `osm_version`, `cr_version` and `jp_version` say what is served.
- **In git, by hand**: `scripts/stations/jp-station-exceptions.csv` (Yahoo matches the rules get wrong), `scripts/routing/jp-rules.csv` (Japanese trains' route choices), `scripts/extract/railway-extract.filter` (what the extracts keep), and the test fixtures in `src/worker/api/fixtures/` (the SQL ones written by the scripts' tests, `UPDATE_FIXTURES=1`).

### Build dashboard (`/build-dashboard`)

A second page of the same Vite build (`build-dashboard/index.html`, `src/build-dashboard/`; the client environment's `rollupOptions.input` in `vite.config.js` lists both pages), with no map code in it. It draws the data build from its state alone: the Worker passes `build/state.json` on as `/build-dashboard/state.json` (`src/worker/build-dashboard.ts`: without the per-file hashes of what each step read, only their number, and without failed steps' last output lines, which stay private) and lists the runs that left a report as `/build-dashboard/runs.json`. `model.ts` reads a step's standing out of the state (done, running, failed, cut off, waiting because a source or an input moved on since it ran, never run; a commit alone does not show, since the repository's files are not in the state), `layout.ts` lays the graph out as a line diagram (sources in the first column, each step a column after the last thing it waits for, long edges through a slot in every column between, columns ordered by their neighbours' heights), and `main.ts` renders the graph, the sources' versions and times, the steps with how long they took and what they wrote, and the recent runs, asking again every minute, or every 15 s while a build runs. Colour there only says where a step stands (the dataviz status colours), with a sign inside the marker; what a node is shows in its shape. A change to what the build writes into the state goes with a change here.

### Tiles

The browser requests `/tiles/openrailwaymap/{z}/{x}/{y}.mvt?v=<version>`, served from the R2 object `openrailwaymap.pmtiles`. `main.ts` asks `/tiles/<archive>/version` for the version at startup (`TILE_URL` is a promise; `vite.config.js` preloads the request, and without an answer the URL carries no version and tiles are cached for a day), so a new archive shows on the next load with nothing to bump or deploy: the version in the URL is what busts browser and edge caches. `?tileset=` overrides the archive name (`TILE_ARCHIVE`). The worker serves tiles gzip-compressed as stored (`Content-Encoding: gzip`); the Cloudflare Vite plugin's dev proxy decompresses them, so `pnpm dev` transfers raw tiles. The archive is built by `scripts/tiles/export-tippecanoe.sh` from the OpenRailwayMap import database image (`ghcr.io/hiddewie/openrailwaymap-import-db`; `scripts/tiles/export-from-image.sh` starts the database from the image, pinned by digest, and runs the export against it), as the data build's `tiles` step, whose `deploy-tiles` uploads it to R2. Railway line relations (`route=railway`), which that database lacks, come from the planet: `lines.opl`, the `railway-extract` step's output (see Data build), which the export loads (`LINE_RELATIONS_OPL`, parsed by `scripts/tiles/line-relations.py`) to add `line_relations` to `railway_line_high`. It also holds the railway ways with their tags, so railway ways' `tracks`, `start_date` and `opening_date` (also missing from the database) reach `railway_line_high` through the `line_way_tags` table. Both line layers also carry `operator_color` (the view's brand color or hashed hue, computed the same way for filled-in operators), and the zoomed-out layer carries `voltage` and `frequency` for the electrification color mode. Station sizes in China come from China Railway's timetable: `cr-station-trains.csv` (the `cr-station-trains` step: `scripts/stations/cr-station-trains.py` matches the timetable's stations to the extract's by name and line kilometres; `CR_STATION_TRAINS` for the export, which skips it when unset) gives trains per day per matched OSM station, and the export's `station_overrides` table turns that into size, importance and the zoomed-out isolation (`discr_iso`) for those stations. Stations in Japan carry `yahoo_codes`, their Yahoo! 乗換案内 station codes from `jp-station-codes.csv` (the `jp-station-codes` step: `scripts/stations/jp-station-codes.py` matches the extract's stations through the API's station search, with `jp-station-exceptions.csv` for what the rules get wrong; `JP_STATION_CODES` for the export), which the Timetable button in their info box (`src/timetable.ts`, client in `src/norikae.ts`) opens; a Japanese station without codes gets no button. Mainline stations with a Chinese name inside China get the same button for China Railway's timetable from the same API (`/api/v1/cr`), which finds the station by the OSM elements in the feature's `osm_id`/`osm_type`, else by its name without 站. In Japan, where OSM has no line relation for about a quarter of the mainline track and names ways inconsistently (`JR外房線` and `外房線`), a way's lines are instead the official lines of MLIT's railway data (国土数値情報 N02, CC BY 4.0, credited in the Credits panel, `credits.ts`) it follows: `scripts/lines/line-groups.sh` runs `line-groups.py` on N02 (downloaded by `scripts/lines/fetch-n02.sh`), which matches ways to N02 lines by geometry with names breaking ties, adds lines drawn on shared track, extends lines along connected track of the same name, and names them from OSM (`山陰本線`, `京成本線`, `つくばエクスプレス`); the export (`LINE_GROUPS_DIR`) lists them in those ways' `line_relations` (ids `jp-…`, replacing their relations) and names the zoomed-out layer's sections after them, while `line_color` stays voted by way name, since an official line holds services of different colors (東海道本線 holds 京浜東北線 track). Line segments without an `operator` tag take the operators of their line relations, or else of their subway/tram/light rail routes (`line_operators` in the export script), because China's railway bureaus and Shanghai Metro mostly tag the operator only on relations. The script only depends on that database's schema, not on OpenRailwayMap source files, but it is coupled to this repo: its layer names and attributes are what the style, the railway filter, the route highlight and the popups read, and its per-layer zoom filters mirror the zooms the style draws each layer at, so change them together. The archive is several GB, so an upload by hand needs an S3 client against the R2 endpoint, since `wrangler r2 object put` caps at 300 MiB.

### Browser app (`src/main.ts`)

`main.ts` merges the OpenFreeMap base style with the OpenRailwayMap style, adds hillshade, contours and satellite imagery, sets the globe projection with a sky/atmosphere (space backdrop is CSS on `#map`), and wires feature modules, each exposed as an `install*`/`create*` function: GPX/GeoJSON import (`gpx.ts`), popups (`popup.ts`, structured sections for lines and stations, on phones a bottom sheet, as the panels from `map-panel.ts` are (`bottom-sheet.ts`: sheets open at half the map's height, so what they draw keeps the upper half, and drag up to nearly all of it or down to their head; only the latest opened shows, covering the earlier ones until it closes); lines drawn below z7 come from a layer without route or line lists, so a click there looks them up in the z7 tile with `route-trace.ts` `lineListsNear`), Photon search, weather picker, the Locate readout (`cursor-position.ts`: coordinates and DEM elevation under the pointer, sampled from the contour lines' terrain tiles), the railway filter, the Layers panel (`map-layers-panel.ts`), and the annotation renderer and tools. The Annotations panel (`annotation-tools.ts`) also holds the layer list with GPX/GeoJSON import: `layer-manager.ts` has no panel of its own and is mounted there, active only while that panel is open. Selecting an annotation layer in the list picks where new annotations go. The Route annotation tool calls OSRM through `osrm.ts`. `LayerStore` (`src/layer-store.ts`) is the in-browser state for layers and features. Use `src/style-ready.ts` helpers when touching the map style, because imports can arrive before the style has loaded.

Routes, lines and trains come from the API (`norikae.ts`, `/api/v1/doc.md`), which answers in OSM ids the tiles share. A request that failed in a way asking again may fix (`isRetryable`: network errors and 5xx, not 404 or 400) gets a Retry button by its message (`retryButton` in `map-panel.ts`); the client drops failed answers from its cache, so a retry asks the API again. Selecting a route or line in an info box highlights it from the tiles' route lists (`route-highlight.ts`) and opens the route panel beside the map, which fills from `/api/v1/relations/{id}` (operator, ends, length, links, its stations in order, the extent to zoom to) and takes the zoomed-out outline from it too, tracing it through z7 tiles (`route-trace.ts`) only when the API has nothing. A route's master opens in the panel too, listing its routes; no tile lists a master, so its outline draws at every zoom. Japanese departures show each train's name, badges for trains starting there and with a Green Car, cars and track, or, behind a remembered switch, a printed timetable's layout (an hour a row, each minute under its type and destination marks, with a legend); a train opened from one carries its number, cars and track into its facts. A China Railway station's trains show under the number they run as there, and two rows of tabs in the back row filter them, one by line and one by 上行/下行 (`crLineTabs`, `crBoundTabs`, from the API's `line` and `bound`); a train's stops mark where its number changes. A China Railway train in the timetable also shows, behind a switch the browser remembers, each stop's km and the lines between two stops (`crLinesBetweenStops`, from the schedule's `lines`), and the trainset 12306 assigns (`/api/v1/cr/trainsets`, asked live once the train shows), which replaces the rolling stock the schedule plans, since the two often name different models. A train opened in the timetable (`timetable.ts`) draws its track from the train route endpoints (`train-route.ts`): the ways it covers whole are the tiles' own features, picked by setting the train route layers' filter to their ids, and the rest (outline below z7, partly covered ways, legs without a path, stops) is a GeoJSON source; those layers live with the highlight's, and a `trainRouteShown` global state dims the other railways as a highlight does. Both label their stops (from the API's stop list) in layers at the very top of the style, so those labels win placement over the other railway and base map labels, which fade meanwhile; station names other than the route's or train's go, and the tiles' own label of a stop's station too (matched by name or OSM element through a global state list), so no stop is named twice and nameless stations take no room from other labels, and pointing at a stop in either panel's list marks it on the map (`setStationHover`). Opening a timetable closes the station's info box. The search bar (`search.ts`) asks Photon for places and, for text that could start a train number, the API's `/api/v1/search` for China Railway trains, listed first; a train opens straight into the timetable's train view.

Display settings are applied by rewriting the style once at load and then flipping MapLibre `global-state`, never by editing layers one by one, with two exceptions, the railway color mode (below) and the train route layers' way filter (above). Keep data-driven expressions small: MapLibre copies them into every tile result its workers send, and the main thread unpacks each one, so an expression holding every option of a setting slows every tile down (a station color expression once made railway tiles take up to 350 ms each on the main thread):

- `railway-filter.ts` adds filter clauses to railway line/station layers (heritage lines, `preserved`, count as tourism whatever their usage), an overlay visibility switch and a switch for the style's tunnel covers and bridge railings (off by default, matched by layer id); `railway-filter-panel.ts` is its panel. The vendored style still hides its railway layers whenever the `date` global state is below its default (the year `pnpm generate:style` ran), from upstream's historical view, which this map dropped along with its OpenHistoricalMap layers (their Japanese data mostly dates from 1971); nothing sets `date`, and `main.ts` must not override its default.
- `railway-colors.ts` recolors railway line fills by route color, operator, maximum speed, electrification, gauge or number of tracks instead of usage (the color mode and its legend live in the railway panel). The line layers are built for the chosen mode only, keeping their original color in `metadata` (`orm:recolor`), and switching modes rewrites them with `setPaintProperty` (`applyRailwayColorMode`), which reloads the railway tiles just as a global state change would. The default mode reads a line's color from `line_color`, which the export sets on both line layers to the length-weighted majority color of the routes of every segment with the same name and operator (`line_colors` in the export script), so parallel tracks of one line look alike, and on other segments to the first colored route among their first four, else to the color of the track they join that carries the same routes (`line_neighbor_colors`: a tunnel or bridge named after itself, such as 島田トンネル on 中央本線, gets no vote of its own); lines without it keep the usage color. Station icons follow the lines too (`withRailwayStationColors`): a dot in the line's color in that mode (dark gray otherwise, or without a colored route), or a ringed white dot where routes of different colors stop, from the `station_kind` and `station_color` the export works out from a station's routes (`orm_station_colors`). It picks layers by the ids `railwayLine()` in `scripts/styles/shared.mjs` generates, and each mode's legend table drives both the map colors and the panel legend.
- `map-layers.ts` handles base map / satellite / hybrid visibility, hybrid road and label styling, gray roads unless "Highlight roads" is on (outside hybrid mode), darker, slightly wider base map borders by admin level when "Highlight administrative divisions" is on, plus level 7 (municipalities) that the base style leaves out (OpenRailwayMap has no borders; they are the base map's `boundary_*` layers), base map saturation, label language and terrain layer switches; `map-layers-panel.ts` is its UI, the Layers panel.
- `map-panel.ts` holds the shared panel markup; `stored-settings.ts` persists settings in localStorage.

The map opens at the view in the URL's hash (`#zoom/lat/lng`, which MapLibre keeps in sync); without one, where it was last left on this device (`map-view.ts`, saved once the map settles), and the first time on Tokyo's Yamanote loop.

The attribution line (bottom right) only credits OpenStreetMap and, while imagery shows, Google (`withShortAttributions` in `main.ts` blanks every other source's attribution); its Credits button opens `credits.ts`, which lists every data source and service. Add new sources there. A chip at the top centre (`load-status.ts`) says while railway or base map tiles in view are still loading, with the number left (elevation is left out), and how many tiles in view failed, with a Retry that resets the failed sources' tile URLs, since MapLibre never refetches a failed tile; so an empty area only means no railway once the chip is gone. The counts read each source's tile manager (`map.style.tileManagers`), which MapLibre types but does not document; if that breaks in an upgrade, the chip logs a console error and falls back to `isSourceLoaded` and tile error events.

Zoom curves cannot be nested inside other expressions, so the rewrites map over a curve's stop outputs (`mapZoomOutputs`). Unit tests validate rewritten styles with `@maplibre/maplibre-gl-style-spec` and evaluate the expressions directly.

Leftovers from the collaboration era still shape some modules: `layer-sync.ts` and `file-layer-sync.ts` hold layer ordering and file-layer content helpers used by the layer store and manager, and `collaboration-permissions.ts` gates editing on a `data-collaboration-can-edit` attribute that nothing sets any more, so editing is always enabled.

`src/screenshot-fixture*.ts` is a deterministic demo scene (`?screenshot=overview|layers|annotations`) enabled by the `__SCREENSHOT_FIXTURES__` build flag. E2E tests and `pnpm screenshots` (images in `docs/screenshots/`) depend on it.

### Layer and annotation model

See `docs/layer-stack-design.md` (its storage and sync sections describe the removed room backend). Key rules that still hold in the browser:

- Ordering is only `sortKey` on layer rows (fractional keys from `src/layer-model.ts`).
- Each annotation feature is its own record with a `layerId`. Never store feature arrays on a layer or the whole drawing as one JSON blob.

### Map style

`public/orm/style/standard.json` is generated output. Edit the fragments under `scripts/styles/` and run `pnpm generate:style` instead of editing the JSON. `public/orm/**` is excluded from lint and format. `pnpm generate:style` also cuts the sprites down to the icons the style can draw (`scripts/styles/sprite-subset.mjs` writes `public/orm/{sprite,sdf_sprite}/standard*` and points the style at them); a unit test fails when the subset is out of date. The full `symbols*` sprites stay for the missing-icon fallback in `main.ts`.
